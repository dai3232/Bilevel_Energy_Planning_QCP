# 输出工件与文件命名规范

## run_id

建议格式：`YYYYMMDD_HHMMSS_<stage_id>_<git_short_sha>`。同一 `run_id` 目录不得覆盖。

## 运行目录

`runs/<run_id>/` 下必须包含：

- `run_manifest.json`
- `environment.csv`
- `input_hashes.csv`
- `effective_config.yaml`
- `git_state.txt`
- `iterations/*.csv`
- `indices/*.csv`
- `matrices/matrix_manifest.csv`
- `checkpoints/checkpoint_manifest.csv` 与 MAT 检查点
- `tests/`（正式测试 run 必须包含测试清单、逐项结果、JUnit、完整控制台日志、实际命令、汇总与证据 SHA256 清单；非测试 run 可保留空目录）
- `issues/issue_log.csv`、`decision_log.csv`
- `acceptance/acceptance_results.csv`
- `reports/*.docx`

## 数值存储

- 大型稀疏矩阵：MAT 或 Matrix Market。
- 需要 CSV 审计的稀疏矩阵：`row_index,column_index,value` 三元组。
- 小矩阵：可同时保存二维 CSV，例如小时块、日响应和 16x16 核心。
- 浮点 CSV：至少 `%.17g`。

## 中文 Word 文件名

- `阶段X_模型与优化结果报告.docx`
- `阶段X_问题修复与验收报告.docx`
- `运行_<run_id>_结果摘要.docx`
- `阶段0_测试执行证据补充报告.docx`
- `第一次火电计算结果报告.docx`
- `第二次火电计算结果报告.docx`

## 报告真实性

报告数值必须从本次 run_id 的 CSV/MAT/JSON 自动读取。无数据时写“未运行/不适用”，不得填入预测值。

## Stage 0 测试证据补充 run

补充重跑只证明新 run 中实际执行的测试，不得反向声称证明历史 run 当时的控制台输出。其 `run_manifest.json` 必须记录 `run_purpose=stage_0_test_evidence_addendum`、父 run、历史基线提交、当前代码提交、实际测试命令、测试计数、输入哈希、证据文件及 SHA256，并明确 `optimization_executed=false`、`a1_solver_executed=false`。

`tests/` 至少包含：

- `test_inventory.csv`
- `test_results.csv`
- `test_results.xml`
- `matlab_test_console.log`
- `test_command.txt`
- `test_summary.json`
- `test_evidence_manifest.csv`

补充 run 的 `acceptance/acceptance_results.csv` 只记录 `S0-TEST-EVIDENCE-001`，不得复制或伪装成重新执行历史 Stage 0 阻断性验收。

## Stage A3 递推排列与测试集合证据

Stage A3 正式运行的 `indices/permutation_map.csv` 必须是 4340 行的真实非恒等递推约化排列，`indices/canonical_index_map.csv` 保存完整规范方向语义映射。`matrices/daily_recursive.mat` 必须包含实际分区、正向和逆向排列、装配审计以及七个日链和年度核心到规范约化系统的装配信息；相关条目必须进入 `matrix_manifest.csv`、证据清单和 SHA256 清单。

Stage A3 的正式测试集合由版本控制文件 `tests/stage_A3_expected_test_inventory.csv` 唯一界定。运行前必须动态发现显式指定的 A3 测试文件，并验证测试名、顺序、来源文件和唯一性与该清单完全一致；缺少、重复或未登记测试均阻断正式运行。运行器、正式入口和报告生成门禁必须校验同一清单及其 SHA256。A2、A1 回归数量仍分别严格为 32 和 37。
